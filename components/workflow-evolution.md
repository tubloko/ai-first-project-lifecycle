# Workflow evolution

The workflow is allowed to change, but an active run should not rewrite the rules that judge its own success.

## Propose before changing

When a role discovers a process defect:

1. record the observed failure;
2. preserve the evidence;
3. propose the smallest rule or tool change that addresses it;
4. name the owner of the affected policy;
5. decide whether the current task can continue under the old rule;
6. apply the policy change only through its authority path.

## One active experiment

Running several workflow changes together makes attribution weak. Prefer one registered experiment at a time for questions that matter.

## Pre-register the experiment

Before observing the result, define:

- question;
- hypothesis;
- fixed conditions;
- variable being changed;
- baseline;
- evidence to collect;
- decision criterion;
- possible outcomes, including inconclusive;
- authority that may adopt the result.

Use [Workflow experiment](../templates/workflow-experiment.md).

## Do not convert anecdotes into policy automatically

A useful observation may justify a proposal without justifying a global rule. Distinguish:

- one incident;
- repeated pattern;
- controlled comparison;
- measured improvement;
- policy decision.

## Retire rules

A rule that no longer protects a real boundary becomes context cost. Preserve its history, mark it retired, and point to the replacement rather than leaving both versions active.
